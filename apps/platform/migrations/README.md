# Better Auth bootstrap

`0001_auth.sql` was generated by Better Auth CLI 1.7.17 from `auth.config.ts` and applied transactionally to development and the isolated staging database. It creates the dedicated `auth` schema and core user/session/account/verification tables. Production has not been migrated.

Server configuration is in `src/lib/auth.ts`; Next.js mounts it at `/api/auth/*`. The email-code server slice adds six-digit, single-use ten-minute codes, five incorrect attempts per code, persistent per-IP limits and an atomic per-recipient cooldown (60 seconds, maximum five sends per hour). Codes are hashed. Pending/failed delivery reservations still consume cooldown/quota, so provider failures cannot be used to bypass abuse limits. The connected UI, Expo SecureStore and owner MFA are detailed below; Google/Apple setup, real-device acceptance and full recovery/deletion contracts remain subsequent work.

The platform's ignored `.env.local` holds the development pooled `DATABASE_URL`, direct `DATABASE_URL_UNPOOLED`, a random `BETTER_AUTH_SECRET`, and `BETTER_AUTH_URL=http://localhost:3000`. Schema commands explicitly select the direct URL. These initial credentials are a development bootstrap owner; deploy with scoped runtime credentials after migration/grant policy is established.

From the repository root:

```sh
pnpm --filter @jungle-tribe/platform auth:schema:check
pnpm --filter @jungle-tribe/platform auth:schema:generate migrations/0005_auth.sql
pnpm dev:platform
```

The first command checks the live configured database. Generation refuses to overwrite an existing migration. Review and apply generated SQL through the intended branch's direct connection, then rerun the schema check. Generation does not apply migrations.

The `dash()` plugin is inactive until `BETTER_AUTH_API_KEY` is provided. Connecting Better Auth Infrastructure permits user/session administration and sends authentication events to that service. Do not enable it or expose a local server through a tunnel without the owner's confirmation. A localhost-only smoke check confirms `/api/auth/ok` returns `{"ok":true}` and an anonymous `/api/auth/get-session` returns `null`; this does not verify sign-in flows.

## Email-code server slice (#46)

`0002_email_code_limits.sql` adds Better Auth’s persistent IP rate-limit table and the atomic recipient delivery reservation table. It was applied transactionally to development and isolated staging; production still needs its reviewed migration and scoped runtime grants. The live development schema check passes. The additional delivery table is application-owned and is not generated by Better Auth’s schema CLI.

`RESEND_API_KEY` must be a sending-only key restricted to `jungletribe.app`; messages come from `Jungle Tribe <hello@jungletribe.app>`. Sending runs in an awaited request hook because the provider library’s background-task helper swallows errors. Failed delivery returns 503 with no provider payload, credentials or code in logs. Plain-text emails state purpose, expiry and what to do if unsolicited.

Use HTTP `POST /api/auth/email-otp/send-verification-otp` with `{ "email": "collector@example.com", "type": "sign-in" }`, then `POST /api/auth/sign-in/email-otp` with `{ "email": "collector@example.com", "otp": "<six digits>" }`. Successful verification proves email ownership and creates a regular collector session. This slice does not populate profile first/last names or grant administrative permissions. No automatic provider linking is enabled. Read `/api/auth/get-session`, `POST /api/auth/sign-out`, or `POST /api/auth/revoke-sessions` using the session cookie. The latter revokes every session, including the current one.

Web cookies are host-only, HttpOnly, SameSite=Lax and Secure on HTTPS, with a rolling seven-day expiry and cookie caching disabled for immediate revocation. The web client must use credentialed requests to its environment’s API. The API permits only exact configured origins and serves credentialed CORS/preflight without wildcards; do not disable origin validation. Same-site website/API subdomains are the deployed topology. On Vercel, IP tracking trusts only `x-vercel-forwarded-for`, which Vercel sets. Other direct deployments share a counter until a trustworthy ingress header is configured.

Run `pnpm --filter @jungle-tribe/platform test:auth` with `AUTH_TEST_DATABASE_URL` pointing at disposable PostgreSQL. `test:auth:local` explicitly uses the development direct URL from the ignored local environment. Tests create a unique `auth_test_*` schema, use synthetic email addresses with a fake delivery sink, and drop only that schema afterward. They never send mail or mutate real auth rows. GitHub CI provisions PostgreSQL 17 for this suite. Local validation also includes `pnpm check` and `auth:schema:check`.

Before production release: configure production credentials/runtime roles, verify native device sign-in and owner enrollment, and choose cleanup/retention for expired verification and abuse-limit records. The sole approved superadmin identity and policy are recorded in [#5](https://github.com/cereallarceny/jungletribe/issues/5#issuecomment-6644944287); no email-only elevation is provided here.

## Connected client and superadmin MFA (#48)

The consumer welcome/sign-in/check-email states now call the email-code API. They retain real wrong/expired-code feedback, explicit resend and change-email actions, paste/autofill, duplicate-submit guards and both sign-out actions. Apple/Google remain unavailable until provider registration, as approved by the owner. Shared controls follow the repository’s 48px/button and field-spacing contract; assets are exact Figma downloads. Native uses the version-matched Better Auth Expo adapter and SecureStore with a separate prefix per API environment and no cached session payload. The app registers `jungletribe://`; web keeps API-host cookies. All auth requests have a ten-second client timeout.

`0003_superadmin_mfa.sql` combines generated Better Auth TOTP tables with application-owned grants, session proofs and account-level factor-attempt quotas. It was tested in disposable schemas, then applied transactionally to development and the isolated staging database (Neon branch `preview`, `br-spring-credit-bbyilg6m`). No production migration or promotion is part of this change.

`SUPERADMIN_EMAIL` is a server-only eligibility setting. Verified email ownership alone gives an ordinary session. Only successful Better Auth TOTP or single-use recovery verification may create the server-owned `superadmin` grant and an `adminSession` proof. The proof belongs to one session, expires after 15 minutes and disappears when its session is deleted. `/api/admin/session` supplies the caller’s setup/challenge status; `/api/admin/access` is a protected boundary that rejects anonymous, ordinary, email-only, expired-proof and newly signed-in sessions. Every future administrative operation must enforce this server policy before returning private data or mutating anything; a client-side role check is insufficient.

MFA enrollment requires a verified owner primary session created within ten minutes. The owner alone may use MFA endpoints. Five factor attempts per five minutes are reserved atomically per account, independent of IP and session. The owner cannot use email access alone to retrieve the enrolled TOTP URI, disable mandatory MFA or regenerate recovery codes. Trusted-device bypass is disabled. Backup-code regeneration requires a fresh MFA proof. Better Auth encrypts TOTP secrets and recovery codes at rest; the browser generates the enrollment QR locally and never sends its URI to a QR service. Enrollment secrets and recovery codes are transient UI state, not ordinary local storage. The owner must enroll on their own device; nobody should paste codes or secrets into chat.

Hosted staging uses Vercel preview variables scoped only to `staging`: `DATABASE_URL`, a distinct `BETTER_AUTH_SECRET`, `RESEND_API_KEY`, `SUPERADMIN_EMAIL`, and the existing public auth/website origins. Database runtime role `jungletribe_staging_auth_runtime` has auth-schema usage and table DML only; it cannot create schema objects, roles or databases and has no RLS bypass. The database-owner role was not deployed. Because tables are owned by the staging migration role, schema grants and default privileges were applied explicitly; see `grants/staging-auth-runtime.sql`. Production secrets and deployment remain a separate release step. Feature previews do not inherit staging credentials.

For reproducible browser verification, run `AUTH_TEST_USE_DEVELOPMENT=1 node --env-file=.env.local --import tsx tests/ui-server.ts` from `apps/platform`, then run the Expo website with `EXPO_PUBLIC_API_URL=http://localhost:3001` on port 8081. This fixture refuses hosted/production execution, binds loopback only, permits only `@example.test` recipients, fakes delivery and owns a disposable `auth_ui_*` schema. Its loopback `/__fixture/inbox` is synthetic test data only. Stop it with Ctrl+C to drop that schema; it never sends real mail or edits real user rows. The normal integration suite now contains 15 scenarios covering MFA eligibility, enrollment, session binding/freshness, recovery consumption, bounded guesses and native-style requests as well as the earlier sign-in controls.

`0004_admin_totp_replay.sql`, tested and applied separately to development and staging, adds a per-owner, HMAC-only record for each successfully used authenticator code. A code cannot unlock another session during its acceptance window; atomic insertion handles concurrent attempts. Records expire after two minutes and are pruned on later successful factor checks. Better Auth still performs all TOTP and recovery-code verification. The application adds replay prevention and administrator authorization, not a separate authenticator implementation.


## Production release — November 5, 2026

The owner authorized promotion of the tested authentication release from staging to main. Production is the existing Neon branch `br-still-truth-bbczw2cn`, database `jungletribe`. Its auth schema was empty before this release. Reviewed migrations 0001–0004 were applied together in one transaction as `jungletribe_owner`; eleven auth tables now exist. The earlier sections above describe implementation-time staging acceptance; production migration statements there are historical.

Production uses a distinct `jungletribe_production_auth_runtime` role. Catalog checks performed as that role verified auth usage and DML on every auth table, no auth CREATE privilege, no superuser/create-role/create-database/RLS-bypass flags and no `neon_superuser` membership. The owner credential is never deployed. The reviewed explicit grant policy is `grants/production-auth-runtime.sql`; default privileges belong to `jungletribe_owner`.

Vercel production-only API variables are `DATABASE_URL` (pooled runtime connection), a fresh `BETTER_AUTH_SECRET`, `RESEND_API_KEY` (existing sending-only domain credential), `SUPERADMIN_EMAIL`, `BETTER_AUTH_URL=https://api.jungletribe.app` and `BETTER_AUTH_TRUSTED_ORIGINS=https://jungletribe.app`. Production web uses `EXPO_PUBLIC_API_URL=https://api.jungletribe.app`. Staging keeps its own database role, auth secret, accounts and MFA material. The optional Infrastructure dashboard is not enabled on hosted production.

After main deployment, verify anonymous auth health/session/admin rejection and exact-origin CORS. The owner must sign in to `https://jungletribe.app`, enroll an authenticator and save separate production recovery codes privately. Do not copy staging identities, sessions, grants or factor records. Record completed owner acceptance separately from release/build evidence. Google/Apple setup and actual native-device runtime remain subsequent work. Cleanup/retention automation for expired auth/abuse records remains an operational follow-up; this release makes no retention-policy change.

The web favicon is rendered from the approved logo patch SVG. The 512px PNG at `apps/mobile/assets/auth/jungletribe-icon.png` is also suitable for manually assigning a 1Password item icon. 1Password's automatic rich-icon database is separate from the website favicon.


## Google sign-in — November 5, 2026 (#55)

Google Auth Platform is configured in the existing Jungle Tribe project `jungle-tribe-454620` under the owner's account; Trader was not modified. The owner explicitly approved Google's User Data Policy, basic-identity access, separate web clients and sensitive Vercel storage. An unused initial production client was deleted with explicit owner confirmation and replaced before it was ever connected to the app. Active clients are named Jungle Tribe — Production and Jungle Tribe — Staging, with exact matching website origins and API `/api/auth/callback/google` redirects. No development, wildcard or preview callbacks are registered on these clients.

`GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` form a complete server-only pair. They are production-scoped or preview-scoped to staging, respectively; feature previews inherit neither. `/api/auth/providers` exposes only availability. Google requests only openid/email/profile, uses PKCE and online access, and rejects custom/additional scopes or authorization parameters. Access/refresh tokens are encrypted by Better Auth. Google app audience remains External/testing. Google documents an exception to test-user restrictions for basic identity scopes; no production publishing/brand verification is claimed by this setup.

Existing email accounts are never implicitly merged. A recently signed-in, verified collector must explicitly connect a Google identity with the same verified email; the owner additionally requires fresh MFA proof. Different emails and unverified Google claims are rejected. Unlinking is outside this slice and disabled. New Google sessions are ordinary sessions and cannot inherit superadmin proof; the existing factor/grant/session policy still applies. Email remains available as a sign-in method.

Google's light button uses its official G asset and Google Sans Medium with its required spacing/color treatment, retaining the shared 48px touch target. Source: https://developers.google.com/identity/branding-guidelines . Other controls retain the approved Jungle Tribe measurements. Client errors display safe retry/email guidance, including cancelled consent and account-not-linked callbacks.

The six new HTTP cases use disposable PostgreSQL schemas and fake only Google's token-exchange transport; Better Auth state/PKCE, callbacks, sessions, linking and authorization run normally. They do not establish real Google consent or native-device acceptance. Those require owner verification after deployment. Apple is still deferred. The exact registered callbacks are https://api.jungletribe.app/api/auth/callback/google and https://staging-api.jungletribe.app/api/auth/callback/google .
