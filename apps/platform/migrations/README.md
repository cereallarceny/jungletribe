# Better Auth bootstrap

`0001_auth.sql` was generated by Better Auth CLI 1.7.17 from `auth.config.ts` and applied transactionally to the **development** branch only. It creates the dedicated `auth` schema and core user/session/account/verification tables. Preview and production have not been migrated.

Server configuration is in `src/lib/auth.ts`; Next.js mounts it at `/api/auth/*`. The initial project bootstrap has no enabled sign-in methods. Apple/Google/email OTP, the Expo client, owner-only administration with MFA, and recovery/session policies remain implementation work under the authentication decision.

The platform's ignored `.env.local` holds the development pooled `DATABASE_URL`, direct `DATABASE_URL_UNPOOLED`, a random `BETTER_AUTH_SECRET`, and `BETTER_AUTH_URL=http://localhost:3000`. Schema commands explicitly select the direct URL. These initial credentials are a development bootstrap owner; deploy with scoped runtime credentials after migration/grant policy is established.

From the repository root:

```sh
pnpm --filter @jungle-tribe/platform auth:schema:check
pnpm --filter @jungle-tribe/platform auth:schema:generate migrations/0002_auth.sql
pnpm dev:platform
```

The first command checks the live configured database. Generation refuses to overwrite an existing migration. Review and apply generated SQL through the intended branch's direct connection, then rerun the schema check. Generation does not apply migrations.

The `dash()` plugin is inactive until `BETTER_AUTH_API_KEY` is provided. Connecting Better Auth Infrastructure permits user/session administration and sends authentication events to that service. Do not enable it or expose a local server through a tunnel without the owner's confirmation. A localhost-only smoke check confirms `/api/auth/ok` returns `{"ok":true}` and an anonymous `/api/auth/get-session` returns `null`; this does not verify sign-in flows.

## Dashboard project status

The API key is stored only in the ignored platform environment file.

The temporary tunnel and local servers were stopped after verification, and the local auth origin was restored to `http://localhost:3000`. The dashboard's initial server URL was temporary and will be offline until replaced with the actual hosted API URL. No always-on deployment exists yet. Configure the deployed platform's trusted proxy/IP headers before relying on per-client rate limits; the connection check surfaced that requirement. Evaluate the dashboard's Infrastructure patch-update notice before production delivery.
